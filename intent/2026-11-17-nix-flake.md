# Intent: Install and configure omateams from this fork's own flake

## Problem

- **The NixOS configuration builds omateams from the wrong source.** It
  builds from upstream `Divanyx/omateams` at a pinned rev
  (`~/.config/nixos/pkgs/omateams/default.nix`). This fork
  (`olafkfreund/omateams`) is where fixes now land, starting with the memory
  guard in PR #1, so the configuration never gets them.
- **The packaging lives in the wrong repo.** The NixOS configuration holds:
  - the package, which patches `Service.qml` to point at the store binary and
    turn off self-install;
  - the memory-capped `systemd-run` wrapper;
  - a host module (`hosts/common/nixos/omarchy-omateams.nix`) that wires the
    plugin in through home-manager.

  Each change to omateams means editing a rev and hash in another repo, and
  none of it is usable by anyone else on NixOS.
- **It runs on a Qt with the bug.** The package builds against nixpkgs'
  `qt6.qtwebengine`, which is `6.140.0-rc` on the pinned nixpkgs and on
  `nixos-unstable`. That version still has QTBUG-142040, the root cause of
  the 180 GiB runaway. `6.140.0` final, which fixes it, is in nixpkgs
  `master` and already in cache.nixos.org.

## Proposed outcome

- **A flake in this repo.** It provides a package, an overlay, a NixOS
  module and a home-manager module to install and configure omateams,
  including its settings and the plugin. It follows the same shape as the
  owner's other Omarchy apps (`nixarchy-omapod`).
- **The NixOS configuration consumes it as an input.** It drops its own
  `pkgs/omateams` and `omarchy-omateams.nix` wiring, and `omaoutlook` still
  finds the omateams binary.
- **The omateams that gets installed runs on QtWebEngine 6.140.0 or later.**
  Screen sharing no longer terminates the GPU thread's EGL display.
- **Updating omateams means updating the input** (`nix flake update
  omateams`). No rev or hash needs editing.

## Affected users and systems

- This repo: a new `flake.nix` and Nix files. No change to the app's code.
- The owner's NixOS configuration:
  - `flake.nix` inputs;
  - `pkgs/omateams`, which is removed;
  - `hosts/common/nixos/omarchy-omateams.nix` and `omarchy-omaoutlook.nix`;
  - the hosts that import omateams (p620, razer).
- Hosts p620 and razer, through a rebuild. p510 is not affected.
- Non-Nix users (`install.sh`): unchanged.

## Constraints

- Behaviour has to match the current Nix package:
  - the store-binary patch of `Service.qml`;
  - self-install turned off;
  - the `systemd-run` cap (`MemoryHigh=12G`, `MemoryMax=16G`,
    `MemorySwapMax=0`);
  - the hyprland override;
  - the `BarWidget.qml` colour fix (#2778).
- The sign-in in `~/.local/share/omateams` survives the switch.
- `inputs.nixpkgs.follows` must work for consumers. Getting Qt 6.140.0 must
  not depend on the consumer's nixpkgs being new enough, or the flake must
  say plainly that it does.
- No change outside the owner's NixOS configuration and this repo. The NixOS
  side follows that repo's own workflow and gates.

## Open questions

1. **Where Qt 6.140.0 comes from until `nixos-unstable` has it.**
   - (a) The flake takes QtWebEngine from a pinned nixpkgs revision of its
     own, so a consumer's `follows` doesn't change it.
   - (b) The NixOS configuration overlays `qt6.qtwebengine` from nixpkgs
     `master` for omateams.
   - (c) Wait for `nixos-unstable`.
2. **Scope of the modules.** Which settings the modules expose as Nix
   options (for example `memoryLimit`, `runInBackground`, `closeAction`),
   versus leaving them to `settings.json`.
3. **Order.** Should the flake land after PR #1 is merged, so the first
   flake build carries the memory guard?
