# Intent: Install and configure omateams from this fork's own flake

## Problem

- **The NixOS configuration builds omateams from upstream.** Evidence is
  from the `nixos-omateams-cap` worktree of `~/.config/nixos`.
  `pkgs/omateams/default.nix:21-24` fetches `Divanyx/omateams` at rev
  `e8264d1`. Fixes made in this fork (`olafkfreund/omateams`), starting with
  the memory guard in PR #1, are not in that pin.
- **Packaging lives outside this repo.** That configuration holds:
  - the package, which patches `Service.qml` to the store binary, turns off
    self-install, fixes `BarWidget.qml` and adds the `systemd-run` wrapper;
  - a host module (`hosts/common/nixos/omarchy-omateams.nix`) that wires the
    plugin in through home-manager.

  Updating omateams means maintaining a rev and hash in another repo, and the
  packaging is not offered from this repo.
- **The Qt it builds against still has the bug.** It uses nixpkgs'
  `qt6.qtwebengine`. Verified this session:
  - `nix eval` gives `6.140.0-rc` for the pinned nixpkgs (`f5c082a`) and for
    `nixos-unstable`, and `6.140.0` for nixpkgs `master`.
  - The `master` store path is in cache.nixos.org (narinfo returns 200).
  - On code.qt.io, the `v6.140.0` tag's Chromium has no
    `EglTerminate(egl_.display)` in `egl_dmabuf.cc`, and `v6.140.0-rc` still
    has it. That call is QTBUG-142040, the suspected root cause of the
    180 GiB runaway (see the PR #1 spec).

## Proposed outcome

- **NixOS and home-manager users can install and configure omateams from
  this repo reproducibly**, with the plugin integrated as today.
- **The owner's NixOS configuration gets omateams from this fork.** It no
  longer keeps its own copy of the packaging, and updating omateams needs no
  hand-edited rev or hash.
- **The installed omateams runs on a QtWebEngine with the QTBUG-142040 fix.**
  The acceptance check is at runtime: share and stop several times, with no
  `eglCreateSync failed` and flat host memory.

## Affected users and systems

- **This repo:** new Nix files. No change to the app's code is intended.
- **The owner's NixOS configuration:**
  - its flake inputs;
  - `pkgs/omateams`;
  - `hosts/common/nixos/omarchy-omateams.nix` and
    `hosts/common/nixos/omarchy-omaoutlook.nix`;
  - the hosts that import them.

  It changes under that repo's own workflow and gates.
- **Hosts that run omateams:** p620 and razer, per the imports. This is to
  be confirmed in the spec, and p510 needs the owner's OK before any build.
- **Non-Nix users (`install.sh`):** unchanged.

## Constraints

The switch must keep everything the current Nix package and module give the
user:

- **Plugin and store binary:** the plugin's `Service.qml` launches the store
  binary, self-install stays off, and `install.sh` is not shipped in the
  plugin.
- **Packaged files:**
  - the desktop entry, the icon and the plugin payload;
  - the runtime commands on `PATH` (Hyprland, matching the system's Hyprland
    package, plus libnotify, coreutils and bash);
  - the `BarWidget.qml` colour fix (#2778).
- **Memory cap:** the host starts in the `systemd-run` scope (`MemoryHigh=12G`,
  `MemoryMax=16G`, `MemorySwapMax=0`). Without a user bus it falls back to an
  unscoped start, as today.
- **Version:** the packaged host and the plugin's `manifest.json` report the
  same version. Otherwise `Service.qml:169-174` replaces the host on every
  plugin load.
- **Plugin enable and start-up:** the plugin is registered and enabled once
  per host, as `omarchy-enable-once.nix` does today. Hidden start at login
  keeps following the `runInBackground` setting.
- **State:** the Teams sign-in and Chromium profile in
  `~/.local/share/omateams/`, and the user's existing preferences, survive
  the switch.
- **omaoutlook:** opening Teams invitations from omaoutlook keeps working. It
  needs the same omateams binary, built against the system Hyprland.
- **Consumers:** using `inputs.nixpkgs.follows` must not silently bring back
  an unfixed Qt, or the flake must say plainly what it needs.

## Open questions

1. **When the Qt fix ships.** Must it reach the hosts now, before
   `nixos-unstable` moves past `6.140.0-rc`, or is waiting acceptable?
2. **Who owns settings.** Today the shell UI writes them to `shell.json` and
   `Service.qml` passes them on to the host. There are three options for
   Nix's role:
   - set them and keep them fixed;
   - supply first-run defaults only;
   - stay out of settings.
3. **Order.** Should the flake land after PR #1 is merged, so its first build
   carries the memory guard?
